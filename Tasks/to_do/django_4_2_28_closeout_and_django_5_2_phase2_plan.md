# Закрытие security-task Django 2026-02-03 и план Phase 2 (Python 3.10+ / Django 5.2)

## Цель

Формально закрыть текущую security-задачу после апгрейда до Django 4.2.28 и подготовить/согласовать исполнимый план следующего этапа: переход на Python 3.10+ и Django 5.2 LTS без регрессий.

## Контекст (как сейчас)

- Ветка `club` уже содержит апгрейд до `Django 4.2.28` и сопутствующие правки совместимости.
- Локально подтверждён прогон `manage.py test` и `manage.py check` в подготовленном окружении.
- Деплой в продакшн в этом проекте берёт код из ветки `club`.
- Требуется формализация результата и постановка следующей фазы, чтобы не остаться на промежуточной версии без сроков и владельцев.

## Объём и допущения

- В объёме:
  - формальный closeout по security-релизу от 2026-02-03;
  - подготовка артефактов rollout/monitoring/rollback;
  - отдельный исполнимый план Phase 2 (Python 3.10+ / Django 5.2 LTS).
- Вне объёма:
  - непосредственное выполнение миграции на Django 5.2 в этом плане;
  - изменение бизнес-логики вне задач совместимости.
- Допущения:
  - текущий продакшн продолжает работать на Django 4.2.28 до завершения Phase 2;
  - SRE/DevOps предоставляют доступ к метрикам и журналам для закрытия rollout-пункта.

## План работ

1. Сформировать closeout-пакет текущего апгрейда
- Зафиксировать, какие CVE покрыты апгрейдом и почему.
- Зафиксировать список коммитов/PR, которыми это сделано.
- Сохранить краткий статус: что подтверждено тестами, что подтверждено на staging/prod.

2. Зафиксировать остаточные риски и критерии закрытия
- Описать, какие риски остаются до полного закрытия security-task.
- Для каждого риска указать owner, дедлайн и критерий “закрыто”.

3. Подготовить production closeout checklist
- Проверка after-deploy метрик: 5xx, p95, память, CPU, рестарты воркеров.
- Проверка auth/CSRF/payments/webhook/queue сценариев.
- Подтверждение стабильности в наблюдаемом окне (например, 24 часа).

4. Подготовить и завести отдельный план Phase 2
- Целевое состояние: Python 3.10+ и Django 5.2.x LTS.
- Разделить на этапы: runtime uplift -> dependency uplift -> framework uplift -> verification.
- Прописать блокеры и условия входа/выхода по каждому этапу.

5. Согласовать release governance
- Определить, через какой pipeline и кто даёт final approval на Phase 2.
- Зафиксировать окна релизов, правила canary и критерии rollback.

6. Подготовить execution backlog для Phase 2
- Создать задачи по компонентам: CI, Docker image, dependencies, app compatibility, observability.
- Для каждой задачи: оценка, owner, зависимость, DoD.

7. Провести финальный review плана
- Проверить, что план Phase 2 реализуем за 1–2 итерации без критичных “неизвестных”.
- Вынести все “неясности” в список решений с датой эскалации.

## Корнеркейсы

1. Security-task закрыт формально, но без подтверждённого окна стабильности в проде.
2. Метрики есть, но нет baseline для сравнения до/после.
3. Разные окружения (dev/staging/prod) расходятся по настройкам и ломают доверие к проверкам.
4. Часть интеграций редко используется и не покрыта smoke-сценариями.
5. Для Phase 2 часть зависимостей не поддерживает Python 3.10+.
6. Для Phase 2 часть зависимостей не поддерживает Django 5.2.
7. В CI остаются старые версии инструментов, которые скрывают будущие проблемы.
8. Rollback на Phase 2 усложняется из-за schema/migration drift.
9. Ответственные команды не согласовали единые критерии “готово к релизу”.
10. План перегружен и не имеет минимального инкремента, пригодного к быстрому запуску.

## Вопросы/Неясности

1. Кто финально подтверждает закрытие security-task: backend lead, security или SRE?
2. Какое минимальное окно наблюдения после деплоя принимаем как достаточное?
3. Есть ли уже корпоративный стандарт по обязательным gate’ам перед переходом на новую LTS ветку?
4. Кто владелец этапа Python uplift (инфра или backend)?
5. Нужен ли отдельный dry-run Phase 2 в staging clone с production-like нагрузкой?

## Решения по корнеркейсам/вопросам

- KC1: Security-task закрывается только после checklist + мониторингового окна, не только после merge.
- KC2: Для метрик фиксируем baseline из последнего стабильного релиза и сравниваем с post-release окном.
- KC3: Перед Phase 2 делаем env parity checklist (версии runtime, БД, ключевые env).
- KC4: Для редких интеграций создаём explicit ручные smoke-сценарии и ответственных.
- KC5/KC6: Ранний dependency audit и матрица совместимости как входной gate для Phase 2.
- KC7: CI/toolchain uplift как отдельная ранняя задача, блокирующая framework uplift.
- KC8: Для Phase 2 правило backward-compatible migration only; иначе план двухшагового релиза.
- KC9: Утвердить единый документ acceptance с подписью owner’ов.
- KC10: Сначала выполняем минимальный инкремент: runtime+CI readiness, затем framework uplift.
- Q1: Дефолт — closeout подтверждает backend lead + SRE, security консультирует по CVE-mapping.
- Q2: Дефолт — 24 часа наблюдения после rollout.
- Q3: Если стандарта нет, используем этот план как временный governance baseline.
- Q4: Дефолтный owner Python uplift — infra, backend владеет app compatibility.
- Q5: Да, staging dry-run обязателен перед production Phase 2 rollout.

## Нефункциональные требования

- Трассируемость: каждый пункт closeout должен иметь ссылку на артефакт (лог, dashboard, PR, runbook).
- Проверяемость: критерии закрытия должны быть бинарными (passed/failed).
- Наблюдаемость: обязательные метрики и алерты зафиксированы до начала Phase 2.
- Управляемость рисками: для каждого высокого риска задан owner и fallback.
- Повторяемость: checklist должен использоваться повторно для следующих security-upgrade циклов.

## Тест-план

1. Closeout-тесты текущего этапа
- Подтверждение, что CI зелёный на ветке `club`.
- Подтверждение `check --deploy` для production-профиля.
- Подтверждение smoke-сценариев auth/CSRF/payments/webhooks/queue.

2. Проверка плана Phase 2
- Dry-run ревью матрицы зависимостей (Python 3.10+, Django 5.2).
- Валидация, что для каждого риска есть mitigation + rollback.
- Валидация, что backlog имеет владельцев и сроки.

3. Release readiness
- Таблица gate’ов для входа в Phase 2 подписана owner’ами.
- Канареечный процесс и rollback runbook доступны и проверены.

## Acceptance Criteria (DoD)

1. Security-task по Django release 2026-02-03 имеет формальный status “closed” с артефактами.
2. Есть утверждённый Phase 2 план перехода на Python 3.10+ / Django 5.2 LTS.
3. Для всех high-risk пунктов определены owner, дедлайн и mitigation.
4. Определены и согласованы release gates для Phase 2.
5. Есть валидный rollback runbook и чеклист наблюдения после релиза.

## Риски и rollout/rollback

- Риски:
  - формальное закрытие без операционной верификации;
  - отсутствие owner’ов по критичным блокерам Phase 2;
  - скрытая несовместимость зависимостей при Python/Django uplift.
- Rollout (для Phase 2):
  - readiness -> staging dry-run -> canary -> full rollout.
- Rollback:
  - откат на предыдущий image/tag;
  - rollback framework/runtime только по заранее утверждённой процедуре;
  - при сомнении откатывать приложение, не ломая данные.
