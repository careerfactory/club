# Upgrade plan: Django 3.2.13 -> 4.2.28 (security)

## Цель

Безопасно перевести проект на поддерживаемую ветку Django, закрыть уязвимости из security-релиза от 2026-02-03 (в первую очередь релевантный ASGI DoS), сохранить совместимость текущего функционала и иметь контролируемый rollback.

## Контекст (как сейчас)

- Проект зафиксирован на `django==3.2.13`.
- Production запускается через ASGI: `gunicorn ... club.asgi:application -k uvicorn.workers.UvicornWorker`.
- По коду не обнаружены прямые паттерны `FilteredRelation`, `truncatechars_html`/`truncatewords_html`/`Truncator(..., html=True)`, `django.contrib.gis`/PostGIS raster.
- Основной риск из анонса релизов для этого репозитория: CVE-2025-14550 (DoS через повторяющиеся заголовки в ASGIRequest).

## Объём и допущения

- В объёме:
  - апгрейд Django до `4.2.28`;
  - совместимые обновления django-экосистемы, необходимые для запуска и тестов;
  - фиксация зависимостей в lock-файле;
  - прогон unit/integration/smoke тестов;
  - staged rollout + rollback-план.
- Вне объёма:
  - миграция на Django `5.2.x` (отдельная фаза после подъёма Python);
  - большой рефакторинг старых API без прямой необходимости для апгрейда.
- Допущение:
  - целевая среда может оставаться на Python 3.8 для этой фазы (ветка 4.2 ещё совместима).

## План работ

1. Зафиксировать базовую точку
- Создать ветку `codex/django-4-2-28-upgrade`.
- Снять baseline: `manage.py test`, `manage.py check --deploy`, smoke сценарии логина/платежей/постинга.
- Сохранить baseline-отчёт (какие тесты уже падали до апгрейда).

2. Подготовить dependency matrix
- Выписать все django-related пакеты из `Pipfile/Pipfile.lock`.
- Для каждого проверить совместимость с Django 4.2 и минимально безопасную версию.
- Отдельно проверить `django-q` как потенциальный риск несовместимости.

3. Обновить зависимости
- Обновить `django` до `==4.2.28`.
- Обновить несовместимые пакеты до совместимых версий.
- Перегенерировать lock-файл.
- Зафиксировать изменения только в manifest/lock на этом шаге.

4. Исправить breaking changes конфигурации
- Прогнать проект и устранить ошибки импорта/настроек.
- Проверить middleware/settings на изменения поведения между 3.2 и 4.2.
- Убедиться, что `manage.py check --deploy` проходит для production-профиля.

5. Исправить breaking changes ORM/templating/runtime
- Прогнать тесты и починить несовместимости API.
- Особое внимание: auth, middleware, queryset выражения, template filters/tags, timezone/i18n.

6. Добавить адресные security regression checks
- Добавить тест на устойчивость к повторяющимся заголовкам (ожидаем bounded behavior, без взрывного роста времени/памяти).
- Добавить/настроить ограничение заголовков на уровне reverse proxy (Nginx/Ingress), если ещё не задано.

7. Полный прогон в CI
- Unit + integration тесты.
- `check --deploy`.
- Быстрый DAST/smoke на auth и state-changing endpoint’ы.

8. Подготовить rollout
- Выкатка в staging.
- Сравнение ключевых метрик: latency p95, 5xx, memory/CPU, worker restart rate.
- Канареечный запуск в production на части трафика.

9. Production rollout
- Полный rollout после стабильного канареечного окна.
- Усиленный мониторинг 24 часа.

10. Post-rollout
- Закрыть security task по релизу от 2026-02-03.
- Создать follow-up план: Python upgrade + переход на Django 5.2 LTS.

## Корнеркейсы

1. `django-q` несовместим с Django 4.2 и ломает фоновые задачи.
2. Изменение поведения middleware вызывает неожиданные redirect/CSRF эффекты.
3. Старые template tags/filters падают на новых проверках безопасности/escaping.
4. Неявные deprecation paths становятся runtime-ошибками.
5. Миграции запускаются дольше обычного и блокируют запуск воркеров.
6. Поведение авторизации меняется на edge-case с сессиями.
7. ASGI-стек обновился, но proxy всё ещё пропускает аномальные header-пакеты.
8. Сторонние SDK (payments/auth) привязаны к старым версиям зависимостей.
9. Часть тестов нестабильна и маскирует реальные регрессии.
10. Перегенерация lock-файла подтягивает лишние крупные обновления.
11. Rollback усложняется из-за частично применённых миграций.
12. Разница между dev/staging/prod окружениями даёт ложный зелёный статус.

## Вопросы/Неясности

1. Можно ли на этой фазе поднимать Python (3.10+) или строго остаёмся на 3.8?
2. Есть ли production/staging reverse-proxy конфиг в этом же репозитории?
3. Допустимо ли временно заменить `django-q`, если совместимость не подтвердится?
4. Какое окно релиза и допустимая длительность канареечного этапа?
5. Какие бизнес-критичные сценарии считаются блокирующими для релиза (top-5)?

## Решения по корнеркейсам/вопросам

- KC1: Если `django-q` несовместим, фиксируем два варианта.
  - A (дефолт): обновление до совместимой версии/форка с минимальным diff.
  - B: временное переключение критичных periodic jobs на альтернативный воркер, чтобы не блокировать security upgrade.
- KC2: Для middleware/CSRF заранее собираем smoke-набор форм/POST endpoint’ов и сравниваем до/после.
- KC3: Для template-тегов включаем тесты рендеринга ключевых страниц и email-шаблонов.
- KC4: Все deprecation warning, которые становятся error, конвертируем в отдельные задачи и закрываем в рамках PR.
- KC5: Миграции выполняем до переключения трафика; если длительные, используем maintenance window и pre-run на staging-клоне.
- KC6: Проверяем login/logout/session rotation + remember-me на staging с реальными cookie-политиками.
- KC7: На прокси включаем лимиты на размер/число заголовков; мониторим 4xx spikes и 5xx на app.
- KC8: Любые SDK-конфликты фиксируем через явные constraints в lock и регрессионные тесты платежей/интеграций.
- KC9: Нестабильные тесты помечаем и устраняем до релиза; нельзя выпускать security upgrade с “known flaky red”.
- KC10: Перегенерацию lock-файла ограничиваем: сначала целевой bump Django + необходимые транзитивные фиксы, без широкого массового апдейта.
- KC11: Rollback-правило: только backward-compatible миграции; если нет, rollout блокируется до безопасной схемы.
- KC12: Выравниваем конфигурации окружений через чек-лист переменных и `check --deploy` на каждом этапе.
- Q1: Дефолт — остаёмся на Python 3.8 в этой фазе; Python uplift выносим в Phase 2.
- Q2: Если proxy-конфиг вне репозитория, отдельной задачей запросить SRE-подтверждение лимитов headers до production rollout.
- Q3: Временная замена `django-q` разрешена только для критичных очередей и только с rollback-инструкцией.
- Q4: Канареечный этап не менее 60 минут под обычной нагрузкой.
- Q5: Блокирующие сценарии по умолчанию: login, post create/edit/delete, comment create/delete, payments webhook, daily digest jobs.

## Нефункциональные требования

- Безопасность: переход на поддерживаемую security-ветку Django; проверяем CVE-релевантные пути.
- Надёжность: повторный запуск деплоя идемпотентен; миграции и запуск воркеров не ломают повторный deploy.
- Наблюдаемость: метрики p95/5xx/CPU/RAM + алерты на рост ошибок auth/CSRF/queue.
- Производительность: отсутствие деградации p95 более чем на 10% относительно baseline.
- Операционность: документированный rollback до предыдущего тега/образа.

## Тест-план

1. Локально
- `manage.py test`.
- `manage.py check --deploy` c production settings.
- Smoke: auth flow, создание/редактирование поста, комментарии, платежный happy-path.

2. Staging
- Полный regression pack.
- Нагрузочный тест на ASGI endpoint с повторяющимися заголовками (контролируемый).
- Проверка фоновых задач (`django-q`/queue workers).

3. Production (canary)
- 5xx/error-rate/latency мониторинг.
- Проверка ключевых бизнес-сценариев вручную по чек-листу.
- Проверка webhook-путей и очередей.

## Acceptance Criteria (DoD)

1. В зависимостях зафиксирован `Django == 4.2.28` и совместимые версии связанных пакетов.
2. CI зелёный: тесты + `check --deploy`.
3. На staging подтверждена работоспособность критичных сценариев без регрессий.
4. На production после канареечного окна нет значимых деградаций метрик.
5. Есть документированный и проверенный rollback runbook.
6. Security task по релизу 2026-02-03 можно закрыть как mitigated/remediated.

## Риски и rollout/rollback

- Основные риски:
  - несовместимость сторонних django-пакетов;
  - скрытые runtime регрессии в auth/queue;
  - неполное покрытие тестами нестандартных сценариев.
- Rollout:
  - staging -> canary -> full production.
- Rollback:
  - откат на предыдущий docker image/tag;
  - rollback только при безопасных backward-compatible миграциях;
  - при сомнении оставлять новую схему БД и откатывать только приложение.
